Multi-Group Collaborative Recovery Primcast atomic multicast · spread recovery payload load across destination groups

The insight

A message to several groups is stored — payload and all — in every one of them.

A message addressed to a GidSet is proposed to all its destination groups (propose() → for gid in dest.iter()). So a multi-destination message physically lives, payload included, in each destination group's log.

When an A-node recovers, the missing multi-dest payloads can therefore come from the other destination groups instead of overloading A's own busy peers.
SKELETON small, authoritative metadata — always from own group PAYLOAD heavy bytes, identical everywhere — offload to co-dest groups

Consequence: co-dest groups can serve the payload (byte-identical — same proposal) but not group A's ordering metadata. That skeleton is tiny and must come from A's own peers. This split is the whole design.

Before vs. after

Today single-group

Every byte — skeleton + payload — comes from A's surviving peers.

Group A peers carry 100% of recovery bytes while still serving live traffic.

Proposed multi-group

Skeleton from A. Heavy payloads pulled in parallel from co-dest groups B, C.

A peers serve only tiny skeletons; payload bandwidth fans out across the cluster.

How it runs — 4 phases

Recovering A-node needs entries [from_idx, to_idx).

  1. Skeleton fetch own group — ask A's peers for {idx, entry_epoch, local_ts, final_ts, msg_id, dest}. Authoritative, contiguous, no payload bytes.
  2. Plan (pluggable) — for each skeleton entry: multi-dest & a co-dest group reachable → route payload to a co-dest group; otherwise (single-dest) → an own-group peer. MultiGroupRecoveryPlanner::plan() decides which group and balances load.
  3. Payload fetch parallel — cross-group CrossGroupPayloadRequest{ gid:A, msg_ids } → CrossGroupPayloadResponse{ payloads, missing }. Any missing falls back to an own-group peer. Never fails on a lagging group.
  4. Reassemble & apply — LogEntry = skeleton + payload, assert payload.msg_id == skeleton.msg_id, sort by idx, check contiguity, recovery_append_batch(), finalize_recovery().

Built to be swappable

The routing algorithm is behind one trait; everything else is additive and flag-gated.

trait MultiGroupRecoveryPlanner {            // swap this = change the algorithm
    fn plan(&self, self_gid, skeletons, reachable_groups, own_peers)
        -> Vec<(MsgId, PayloadSource)>;     // OwnPeer(Pid) | CoDestGroup(Gid)
}
struct CoDestinationPlanner;                    // default: round-robin co-dest

Why it stays correct

  • Ordering is always local-authoritative. Co-dest groups never supply A's idx/epoch/local_ts — only opaque payload bytes keyed by msg_id. Global delivery order untouched.
  • Payload identity. Same msg_id ⇒ byte-identical payload everywhere (one proposal). Reassembly verifies the match.
  • Only safe multi-dest entries offload. The skeleton's dest/final_ts mark eligibility; single-dest & in-flight stay on own peers.
  • Completeness fallback. missing msg_ids re-fetch from own peers — recovery never fails on a lagging co-dest group.
